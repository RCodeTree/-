# Linux 运维 HTTP、TCP 及常用服务探测标准与实操指南

## 一、 探测核心原则与分层模型

服务探测（Health Check）是自动化运维与监控告警的基石。高效的探测机制遵循以下三大原则：

### 1. 三级诊断分层模型
* **L4 网络层**：仅确认 IP 可达与端口监听状态（TCP/UDP 连通性）。
* **L7 协议层**：确认协议握手成功（如 HTTP 状态码、SSL/TLS 证书有效性）。
* **应用/业务层**：确认业务逻辑可运行（如后端数据库/缓存连接正常、返回特定 JSON 报文）。

### 2. 探针类型划分（以 Kubernetes/微服务体系为例）
* **Liveness Probe（存活探针）**：检测进程是否死锁或崩溃。若失败，触发重启。
* **Readiness Probe（就绪探针）**：检测服务是否已准备好接收流量。若失败，从 LB / 服务发现中剔除。
* **Startup Probe（启动探针）**：针对慢启动应用，成功前禁用其他探针。

## 二、 HTTP / HTTPS 探测标准与实例

### 1. 探测标准
| 指标分类 | 正常标准 (Healthy) | 异常标准 (Unhealthy) |
| :--- | :--- | :--- |
| **HTTP 状态码** | `200 OK` 或 `2xx` / `3xx` | `5xx`（服务端错误）、`4xx`（客户端错误，某些特定 401 除外） |
| **响应内容 (Body)** | 包含预期关键字，如 `{"status":"UP"}` | 空响应、502 Bad Gateway 页面、数据库连接报错信息 |
| **TLS/SSL 证书** | 证书有效期 $> 14$ 天 | 证书过期、域名不匹配或自签名无法信任 |
| **响应时间 (RTT)** | $< 1\text{s}$ （应用接口）或 $< 500\text{ms}$（静态资源） | $> 3\text{s} - 5\text{s}$（判定为超时） |

### 2. 实操命令与脚本实例

#### (1) Curl 单行快速检测
```bash
# 1. 获取 HTTP 状态码（超时设为 3 秒）
curl -s -o /dev/null -w "%{http_code}\n" --connect-timeout 3 http://127.0.0.1:8080/health

# 2. 检查 HTTPS 证书剩余有效天数
URL="example.com"
echo | openssl s_client -servername ${URL} -connect ${URL}:443 2>/dev/null | \
  openssl x509 -noout -dates | grep notAfter
```

#### (2) Shell 脚本：状态码与响应体双重验证
```bash
#!/bin/bash
TARGET_URL="http://127.0.0.1:8080/api/health"
TIMEOUT=3

# 提取 HTTP 状态码和 Body 内容
RESPONSE=$(curl -s -w "\n%{http_code}" --connect-timeout ${TIMEOUT} "${TARGET_URL}")
HTTP_BODY=$(echo "${RESPONSE}" | head -n -1)
HTTP_CODE=$(echo "${RESPONSE}" | tail -n 1)

if [ "${HTTP_CODE}" -eq 200 ] && echo "${HTTP_BODY}" | grep -q '"status":"UP"'; then
    echo "OK: Service is healthy."
    exit 0
else
    echo "CRITICAL: Health check failed! Code: ${HTTP_CODE}, Body: ${HTTP_BODY}"
    exit 2
fi
```

#### (3) Kubernetes HTTP 探针配置示例
```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
    httpHeaders:
      - name: Custom-Header
        value: HealthCheck
  initialDelaySeconds: 15
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3
```

## 三、 TCP 探测标准与实例

### 1. 探测标准
* **三次握手**：客户端发送 `SYN` 后，服务器能在指定超时内返回 `SYN-ACK` 并完成握手。
* **超时阈值**：通常连接超时设置为 $1\text{s} - 3\text{s}$。
* **局限性**：TCP 仅代表**网络与操作系统协议栈可达**，无法感知进程假死（如 Java OOM 或数据库连接池满）。

### 2. 实操命令与脚本实例

#### (1) 使用 Netcat (`nc`) 探测
```bash
# -z 零输入/输出模式，-w 3 超时 3 秒
nc -zw3 192.168.1.100 3306
if [ $? -eq 0 ]; then
    echo "TCP Port 3306 is OPEN"
else
    echo "TCP Port 3306 is CLOSED"
fi
```

#### (2) 纯原生 Bash 内置 `/dev/tcp`（无额外依赖）
```bash
# 探测 Redis 6379 端口
timeout 2 bash -c "</dev/tcp/127.0.0.1/6379" && echo "Port Open" || echo "Port Closed"
```

#### (3) Python Socket 连接测试脚本
```python
import socket

def check_tcp(host, port, timeout=2):
    sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    sock.settimeout(timeout)
    try:
        sock.connect((host, port))
        sock.close()
        return True
    except Exception as e:
        return False

if __name__ == "__main__":
    is_up = check_tcp("127.0.0.1", 5432)
    print(f"PostgreSQL Port Status: {'UP' if is_up else 'DOWN'}")
```

## 四、 常用中间件与服务探测标准

| 服务类型 | L4/L7 端口 | 核心探测指令 / 接口 | 健康判决标准 |
| :--- | :--- | :--- | :--- |
| **MySQL** | TCP 3306 | `mysqladmin ping` 或 `SELECT 1;` | 返回 `mysqld is alive` 或查询结果为 `1` |
| **Redis** | TCP 6379 | `PING` 指令 / `INFO replication` | 返回 `PONG` 且 `role` 符合预期的 master/slave |
| **RabbitMQ**| TCP 5672 / HTTP 15672 | `GET /api/healthchecks/node` | HTTP 返回 `200` 且 `{"status":"ok"}` |
| **Kafka** | TCP 9092 | `kafka-broker-api-versions.sh` | 能够读取 Broker API 版本或 Consumer Group 无严重堆积 |
| **DNS** | UDP/TCP 53 | `dig @<server> <domain>` | 在 $1\text{s} - 2\text{s}$ 内返回有效 IP 记录且 `NOERROR` |
| **ICMP** | IP 协议层 | `ping -c 4 -W 2 <ip>` | 丢包率 $< 5\%$，RTT 延迟低于阀值 |

### 各服务实操命令实例：

#### 1. MySQL 数据库
```bash
# 标准方法：使用轻量账号执行 mysqladmin ping
mysqladmin -u healthcheck_user -p'CheckPassword123' -h 127.0.0.1 -P 3306 ping

# 深度验证：执行 SQL 查询
mysql -u healthcheck_user -p'CheckPassword123' -h 127.0.0.1 -e "SELECT 1;" > /dev/null 2>&1
```

#### 2. Redis 缓存
```bash
# 带密码认证的 PING 探测
redis-cli -h 127.0.0.1 -p 6379 -a 'RedisPassword' ping 2>/dev/null
# 输出应为: PONG
```

#### 3. RabbitMQ
```bash
# 使用 Management API 探测节点健康状态
curl -s -u guest:guest http://localhost:15672/api/healthchecks/node
# 输出应包含: {"status":"ok"}
```

#### 4. DNS 服务
```bash
# 检查本地 DNS 服务是否能正常解析外部或内部域名
dig @127.0.0.1 www.baidu.com +short +time=2 +tries=1
```

## 五、 生产环境的最佳实践与防抖规则

1. **抖动抑制（Flapping Prevention）**
   * 单次失败不应立即触发高警或服务重启。
   * **标准逻辑**：连续失败 $N$ 次（如 3 次）判定为 Unhealthy；恢复时需连续成功 $M$ 次（如 2 次）判定为 Healthy。

2. **探测频率与资源控制**
   * **L4/TCP 探测**：可设置为 $3\text{s} - 5\text{s}$ 一次。
   * **L7/数据库读写探测**：建议设置为 $10\text{s} - 30\text{s}$ 一次，防止健康检查连接数过多压垮数据库。

3. **专有健康检查账号与权限隔离**
   * 数据库/消息队列的探测账号应遵循**最小权限原则**（如 MySQL 探测账号仅赋予 `USAGE` 权限，只允许连接与执行简单查询）。
