# Git Merge vs Rebase 学习笔记

## 一、 核心概念比喻
*   **Git 的底层逻辑**：每一次 `commit`（提交）都有一个唯一的**指纹（Hash值）**，这个指纹依赖于它的上一个提交（父节点）。如果父节点变了，Hash值就会全变。
*   **Merge（合并）**：现实派。像两条河流汇合，保留真实的开发时间线和分叉痕迹，最后生成一个“融合节点”。
*   **Rebase（变基）**：强迫症派。像“拔树重栽”，把你的提交“拔”下来，插到目标分支的最顶端。**看起来就像你当初没有分叉一样。**

## 二、 原理与图示对比

### 1. Git Merge (安全，保留历史)
**做法**：强行揉在一起，生成一个新的 `Merge Commit` (M)。
```text
主线：A --- B --- E --- F ---
            \               \
你的分支：   C --- D --------- M (Merge Commit)
```
*   **特点**：保留分叉，历史不重写（C和D的Hash值不变）。
*   **缺点**：如果多人开发，分支图会变成“蜘蛛网”。

### 2. Git Rebase (线性，改写历史)
**做法**：把你的 C 和 D 拔下来，以 F 为地基重新插上去，生成全新的 **C' 和 D'**。
```text
主线：A --- B --- E --- F --- C' --- D'
```
*   **特点**：历史变成一条直线（线性）。
*   **为什么叫“改写历史”？** 因为 C 和 D 的父节点从 B 变成了 F，导致它们的 **Hash值彻底改变**（变成了 C' 和 D'）。Git 实际上丢弃了原来的 C 和 D。

## 三、 核心差异速查表

| 对比项 | `git merge` | `git rebase` |
| :--- | :--- | :--- |
| **历史形态** | 保留分叉，多出一个 Merge Commit | 把提交“重放”到主线顶端，完全线性 |
| **是否改写历史** | **否**（安全，真实反映时间线） | **是**（生成全新的 Commit Hash） |
| **适用场景** | 团队协作、已 push 的公共分支 | 本地未 push 的私人分支、整理历史 |

## 四、 终极避坑指南：为什么“永远别 rebase 公共分支”？
如果在公共分支（如 `develop` 或 `main`）上使用 `rebase`：
1. 你的本地记录变成了 C'、D'。
2. 你的同事本地还保留着旧的 C、D。
3. 当你 push 后，同事拉取代码时，Git 会发现历史对不上，**直接精神分裂（产生大量冲突）**。
4. **结论**：改写公共历史是大忌，会导致团队协作灾难。

## 五、 深入解惑：Rebase 后，原来分出去的分支去哪了？
*   **指针概念**：Git 的分支仅仅是一个指向某个提交的**“轻量级指针”**。
*   **执行 Rebase 后**：
    *   `main` 主分支指针**纹丝不动**，不受影响。
    *   你原来的提交记录（C 和 D）变成了**“悬空提交”（Dangling commits）**。它们还在本地仓库里，但没有任何指针指向它们，在 `git log` 中不可见，就像被踢出了族谱。
    *   `feature` 分支指针移动到了最新生成的 D' 上。原分支路径在历史视图中被抹平了。

## 六、 日常使用场景与口诀

> **📌 一句话口诀**
> 本地没 push 的私人分支，想历史好看用 **rebase**；
> 已经 push、或别人也在用的分支，只 **merge**，永远别 rebase。

*   **场景 1（私人整理）**：自己本地的草稿分支，提交了一堆乱七八糟的 `commit`。👉 **大胆用 `git rebase -i`**，整理成一个干净的提交再推。
*   **场景 2（同步主干）**：要把 `main` 的最新代码合到你的开发分支。👉 **用 `git merge main`**，解决冲突，安全第一。
*   **场景 3（公共协作）**：大家一起用的 `main` / `develop`。👉 **绝对不碰 `rebase`**。

## 七、 补充：Rebase 后悔药 💊
如果 rebase 搞砸了，旧的记录其实没被物理删除。使用 `git reflog` 查看你的历史操作记录，找到旧提交的 Hash 值，然后用 `git reset --hard <旧Hash>` 就能强行拉回原来的状态。

## 八、 实战经验：未提交改动「不属于任何分支」（踩坑总结）

### 1. 现象（真实案例）
在 `master` 上修改了文件并 `merge` 了一次 `test-branch`，随后又 `vim` 改动但**没 commit**。发现切到 `test-branch` 后，这个改动「也出现了」——以为内容混进了 test 分支。

`git log` 长这样：
```text
bafead11  (HEAD -> master, test-branch)   test-branch 的提交
60ef376                                    第一次提交
```

### 2. 根因：分支是指针，工作区只有一个

*   **一个仓库只有一个工作目录**。分支只是指向某个 commit 的轻量级指针（呼应第五节）。
*   **未提交的改动只存在于「工作区」**，它不属于 `master`、也不属于 `test-branch`——它只是**漂浮在当前 commit 之上的一层脏数据**。
*   所以切到 `test-branch` 时，这个未提交改动会**跟着过去**（两分支同 commit、无冲突），看起来像「另一分支也有」——其实那不是分支的内容，是工作区的未提交改动。
*   **分支之间真正不同的，只有「已提交」的东西**；没提交的，永远是公共的。

### 3. fast-forward 合并（为什么两分支重合）

当 `master` 落后于 `test-branch` 时，`git merge test-branch` 会**快进（fast-forward）**：不产生 merge commit，直接把 `master` 指针拉到 `test-branch` 同一点。于是两者指向同一个 commit，暂时**完全重合**。

### 4. 未提交改动的处理（决定它「归属」哪条分支）

| 意图 | 操作 |
| :--- | :--- |
| 改动留当前分支（如 master） | `git add 文件 && git commit -m "..."`（分支指针前进，另一分支停在原处） |
| 不想要这个改动 | `git restore 文件` |
| 想放到另一条分支 | `git stash` → `git switch 目标分支` → `git stash pop` → `git commit` |

> 提交之后，分支才会真正分叉/前进；在那之前，所有未提交改动都是「无主」的。

### 5. 避坑口诀

> **📌 切分支前先 `git status`，确认没有未提交改动。**
> 带脏改动切分支，改动会跟着过去；万一在错误的分支上 `commit`，就会造成「分支没合并、内容混了」的麻烦。

*   `git status`：确认 `modified:` 是未提交还是已提交。
*   `git log --oneline --graph --all --decorate`：用图看清两条分支是否重合在一点。
