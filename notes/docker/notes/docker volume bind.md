# Docker 容器挂载方式详解

> Docker 容器默认的存储方式是**可写容器层**，它依附于只读的镜像层之上，**容器一旦被删除，这一层里的所有数据都会随之丢失**。挂载的核心目的，就是把数据从"易失的容器层"转移到"外部持久化存储"上，让数据与容器的生命周期解耦。

## 一、为什么需要挂载

理解挂载之前，先看清不挂载会发生什么。容器内写入的文件默认落在可写容器层，这一层有两个根本限制：

- **生命周期绑定容器**：`docker rm` 删除容器时，可写层被销毁，数据不可恢复。
- **难以提取**：可写层是每个容器独有的，宿主机或其他容器无法方便地直接读取其中的数据。

挂载就是用来绕开这两个限制的。无论用哪种挂载方式，**从容器内部看，数据都呈现为一个目录或文件**，使用体验一致；区别在于数据**实际落在哪里、由谁管理、生命周期如何**。

## 二、三种主要挂载方式

Docker 提供了三种面向数据持久化的挂载类型：**Volume（数据卷）**、**Bind Mount（绑定挂载）** 和 **tmpfs**。

### 2.1 Volume（数据卷）：Docker 管理的持久化存储

Volume 由 Docker 守护进程创建和管理，数据默认存放在宿主机的 `/var/lib/docker/volumes/` 下，但**官方不建议直接去该路径操作数据**，应通过挂载到容器的方式访问，直接修改宿主机上的卷目录属于未定义行为，可能导致数据异常。

Volume 的生命周期**独立于容器**：容器删除后，卷仍然存在，数据保留。它适合性能敏感的场景和长期持久化需求，因为存储位置由守护进程管理，能获得与直接访问宿主机文件系统相同的原始文件性能。

Volume 本身又分为两种：

| 子类型 | 创建方式 | 宿主机路径 | 管理方式 | 适用场景 |
|---|---|---|---|---|
| **命名卷（Named Volume）** | `docker volume create mydata` 或 `-v mydata:/data` | `/var/lib/docker/volumes/mydata/_data` | 有可记忆的名字，可跨容器复用、备份、迁移 | **生产环境持久化的首选**，如数据库数据、多容器共享配置 |
| **匿名卷（Anonymous Volume）** | `-v /data`（冒号左侧留空）或 Dockerfile 中 `VOLUME /data` | `/var/lib/docker/volumes/随机ID/_data` | Docker 自动分配随机名，**容器删除后卷失去引用，成为孤儿数据** | 一次性临时数据、演示或缓存，不关心持久化 |

> 💡 **核心区别**：命名卷有名字，你能找到它、复用它、备份它；匿名卷没有名字，容器一删就很难定位，只适合用完即弃的场景。

### 2.2 Bind Mount（绑定挂载）：宿主机路径的直接映射

Bind Mount 在宿主机路径和容器路径之间建立**直接链接**，允许访问宿主机上任意位置的目录或文件。它**不受 Docker 隔离**，宿主机进程和容器进程可以同时修改挂载的文件。

这带来了 Bind Mount 的核心特征：

- **实时双向同步**：宿主机上改文件，容器里立刻可见；反之亦然。这是开发调试时"代码热更新"的基础。
- **路径必须预先存在**：挂载的宿主机路径需要提前创建好，否则 Docker 可能将其创建为目录（挂载文件时尤其容易踩坑）。
- **可移植性差**：路径依赖宿主机目录结构，换一台机器路径可能不存在，不适合作为生产环境的数据持久化方案。

Bind Mount 的典型场景是**开发调试、挂载宿主机已有的配置文件、Nginx 静态页面目录**等需要"直接操作宿主机文件"的场合。

### 2.3 tmpfs：内存中的临时存储

tmpfs 挂载**将文件直接存放在宿主机内存中，不写入磁盘**。数据是**临时的**：容器停止、重启或宿主机重启后，数据即丢失，不会在宿主机或容器文件系统中持久化。

tmpfs 只适用于**不需要跨容器会话持久化**的数据，典型用途包括：内存缓存、临时中间数据、处理敏感信息（如凭据，避免落盘泄露），以及减少磁盘 I/O 的场景。它是 Linux 特有的挂载方式。

## 三、三种方式对比

| 特性 | Volume（命名卷） | Bind Mount | tmpfs |
|---|---|---|---|
| **数据持久性** | ✅ 永久，独立于容器 | ✅ 永久，但依赖宿主机路径 | ❌ 容器停止即丢失 |
| **数据位置** | Docker 管理的 `/var/lib/docker/volumes/` | 宿主机任意指定路径 | 宿主机内存 |
| **由谁管理** | Docker 守护进程 | 用户自己 | 内核内存 |
| **可移植性** | 较好（Docker 托管，名字可记忆） | 差（依赖宿主机目录结构） | 较好（不涉及路径） |
| **性能** | 高（绕过联合文件系统） | 最高（直接读写宿主机） | 最高（内存级） |
| **典型场景** | **生产数据**、数据库、多容器共享 | **开发调试**、代码热更新、配置注入 | 敏感临时数据、缓存 |

> 🎯 **一句话选择原则**：**生产持久化用命名卷，开发同步用 Bind Mount，临时/敏感数据用 tmpfs，匿名卷只适合一次性场景**。

## 四、实战语法与进阶用法

### 4.1 `-v` 与 `--mount` 的取舍

Docker 支持两种挂载语法：

**`-v`（短语法）**：

```bash
# 命名卷
docker run -v mydata:/var/lib/mysql mysql:8

# Bind Mount
docker run -v /host/conf:/app/conf:ro nginx

# 匿名卷
docker run -v /data redis:7
```

短语法简洁，但**不报错机制较弱**——如果宿主机路径不存在，Docker 可能静默创建目录，导致意外行为。

**`--mount`（长语法，官方推荐）** ：

```bash
# Bind Mount，路径不存在会直接报错，避免静默创建
docker run --mount type=bind,source=/host/conf,target=/app/conf,readonly nginx

# 命名卷
docker run --mount type=volume,source=mydata,target=/var/lib/mysql mysql:8

# tmpfs，可限制大小
docker run --mount type=tmpfs,destination=/cache,tmpfs-size=100M myapp
```

长语法使用键值对，**类型、源、目标、只读属性都显式声明**，路径不存在时直接报错，比短语法更可控，是生产环境更推荐的方式。

### 4.2 `--volumes-from`：跨容器共享卷

`--volumes-from` 允许一个容器**直接继承另一个容器已挂载的所有卷**，无需重复指定源路径。

```bash
# 容器 A 挂载了数据卷
docker run -d --name data_container -v mydata:/app/data my_image

# 容器 B 继承容器 A 的卷
docker run -d --volumes-from data_container my_other_image
```

它适合多个容器需要共享同一份数据的场景，比如备份容器临时挂载数据库容器的卷来执行 `tar` 备份。支持同时指定多个 `--volumes-from` 来继承多个容器的卷。

### 4.3 只读挂载

在挂载选项后加 `:ro`（短语法）或 `readonly`（长语法），可以强制容器**只能读、不能写**：

```bash
docker run -v /host/conf.yaml:/app/conf.yaml:ro nginx
docker run --mount type=bind,source=/host/conf,target=/app/conf,readonly nginx
```

只读挂载是**安全加固的基础手段**：配置文件、证书、启动参数等敏感路径应默认设为只读，防止容器内进程篡改宿主机文件。

> ⚠️ **容易失效的细节**：`:ro` 限制的是 **mount 标志**，如果容器内进程以 **root 运行**，而宿主机目录权限允许 root 写入，只读标志可能被绕过。真正要让只读"硬"生效，需要**配合非 root 用户运行容器**（`--user`），从文件系统权限层面彻底阻断写入。

## 五、关键注意事项

**1. Bind Mount 会"遮盖"容器内原目录内容。**
当你把宿主机目录挂载到容器内一个**已有内容的目录**上时，容器内该目录下的原有文件会被**隐藏**（不是删除），容器看到的是宿主机的目录视图。如果镜像里该目录有必要的初始文件，挂载前需要确认是否还需要它们。

**2. 数据清理责任不同。**
命名卷需要手动删除（`docker volume rm`）或批量清理（`docker volume prune`），否则会持续占用空间。Bind Mount 的数据清理完全由你负责宿主机目录。匿名卷在容器删除后可能变成孤儿数据，需要靠 `docker volume prune` 清理。

**3. Bind Mount 的"白名单"不能靠 `.dockerignore`。**
`.dockerignore` 只影响**镜像构建阶段**的上下文传输，对**运行时**的 Bind Mount **完全无效**。如果要限制容器能访问的宿主机路径范围，需要**最小化挂载路径**（只挂载具体文件/子目录，而非整个父目录），并配合只读挂载和用户命名空间权限映射来实现运行时隔离。

**4. 挂载文件时，宿主机文件必须已存在。**
用 Bind Mount 挂载单个文件（如 `probe.log`）时，如果宿主机上该文件不存在，Docker 可能将其创建为**目录**，导致容器内程序写入时报错。挂载文件前先 `touch` 创建，或优先挂载目录。

## 六、总结

Docker 挂载的本质是**把数据从"易失的容器可写层"迁移到"外部的、生命周期可控的存储位置"**。三种方式的核心差异在于**数据存在谁的地盘上、由谁管理、容器删了数据还在不在**：

- **命名卷**：Docker 管理，有名字，独立于容器，是生产持久化的默认选择；
- **Bind Mount**：宿主机路径直连，实时同步，是开发调试和配置注入的工具，但可移植性差、需注意路径和权限；
- **tmpfs**：内存临时存储，容器停即丢，只用于敏感或缓存类数据。

实战中，**生产环境优先用 `--mount` 长语法 + 命名卷 + 只读加固**；**开发环境用 Bind Mount 实现代码热更新**；**临时敏感数据交给 tmpfs**。匿名卷除非明确是一次性场景，否则尽量避免依赖。
